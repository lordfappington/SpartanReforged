# LEVEL00 World Render Submission

## Scope and result

This note covers only the canonical LEVEL00 `MODELS` material/geometry submission path in `SLES_533.93`. It stops at the VU1 boundary and does not analyze the microprogram, gameplay, characters, or other renderer systems.

The CPU-side submission order is now **CONFIRMED**. Effective GS `PRIM` state, including `ABE` and `CTXT`, is not generated by the recovered material packet and remains **UNKNOWN** behind a bounded VU1 dependency.

## Material queue and chain

The runtime material manager contains 66 slots of `0x430` bytes. Each slot begins with the resident nine-entry GS state packet and contains a draw-pointer list at `+0x420`, capacity at `+0x424`, queued count at `+0x428`, and a flag at `+0x42c`.

```text
geometry object
  -> FUN_0026fe70 (append by object material index at +0x10)
  -> runtime material pointer list
  -> FUN_0026e700 (emit material packet, then queued geometry chain entries)
  -> FUN_0026ea70 (normal three-range pass builder)
  -> FUN_002590d0 (terminate chain)
  -> FUN_00258d40 / FUN_00258c70 (start VIF1 DMA)
  -> geometry VIF batch MSCALF 0
  -> resident VU1 microprogram entry 0
```

`FUN_00258970` has only two direct callers, `FUN_00258b80` and `FUN_0026d150`; both construct/reset runtime materials. Its packet is resident state, not a draw call. `FUN_0026e700` copies its first DMA/GIF chain entry before every non-empty material's geometry entries. The packet is therefore emitted once per non-empty material per built chain, not once per descriptor or VIF batch.

## Confirmed pass ordering

The normal frame path `FUN_002e0760` calls `FUN_0026d080(0x005a0d30, 1)`, selecting `FUN_0026ea70`. That function emits three ascending-material-index ranges separated by explicit transition packets:

1. indices `[0, 4)`;
2. indices `[4, 21)`;
3. indices `[21, total)`.

The first boundary is initialized to 4. The second is set from MTL child type 15 value 0: the parser reads child type 15 into parsed-material `+0x14`; `FUN_0026f0e0` / `FUN_0026f730` update manager `+0x115fe`; canonical record 21, `AMBIENT_FOLIAGE`, is the type-15=0 marker. This joins executable data flow to the ordered MTL table without inferring the boundary from names.

`CLOUD` is material index 31, so it is **CONFIRMED in the third/special material range and after the ordinary world-material range 4–20**. Within that range it is submitted after indices 21–30 and before indices 32 onward. Thus it follows effect-like records `APP_BLOOD_02` through `LIGHT_SPHERE02`, but precedes `GIBS`, `GRKTREE`, `GREENERY`, and later glow/flare records. No distance or depth sorting exists in these recovered loops; ordering is stable material-index grouping. This proves relative queue order, not an engine-authored name for the pass.

The diagnostic path `FUN_00386620` can call `FUN_0026d080(..., 0)`, which instead uses one ascending-material pass. It is not the normal frame path.

## PRIM and the bounded VU1 dependency

The nine-entry material packet writes context-2 `TEX1`, `TEX0`, `TEST`, `ZBUF`, and `ALPHA`, followed by `PRMODECONT` and `PRMODE`. It does not write GS `PRIM`.

The recovered `PRMODECONT` payload has `AC=1`. Under the GS definition, primitive attributes are therefore taken from `PRIM`, not `PRMODE`. Consequently the material packet cannot establish effective `ABE` or `CTXT`, even though it supplies context-2 state registers.

Each MODELS VIF batch ends with `MSCALF 0`; there is no embedded `MPG`. The CPU chain builder copies the geometry chain unchanged and starts VIF1 DMA. Effective primitive state must therefore be emitted or selected by the resident VU1 geometry program entered at micro-address 0 (or by data consumed there). This is the requested bounded stop condition.

The exact next target is: **the smallest resident VU1 program region reachable from entry 0 for a MODELS batch, limited to GIFtag/PRIM construction and V4-to-RGBAQ routing**. Its upload source/size was not recovered on this CPU-side path and must not be guessed.
